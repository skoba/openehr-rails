## 2. #55: profile id のテンプレートでの修飾

### 2.1 いまの状態(実測)

- id は `ProfileGenerator#profile_id`(`profile_generator.rb:203`)と `FshGenerator#profile_id`(`fsh_generator.rb:203`)に同じ式が 2 つある。
  どちらもアーキタイプ ID だけから作る
- JSON の `name` は `entry[:concept].camelize`(`Height`)、FSH の `Profile:` は id から作る(`OpenehrObservationHeightV2`)。
  **JSON と FSH で name が食い違っている**
- `url` は JSON だけが持つ(`urn:openehr:<archetype_id>`)。FSH は `^url` を書かない(SUSHI の canonical から決まる)
- 3 つめの同じ式が `ResourceRegistry::Entry#slug`(`resource_registry.rb:16`)にあるが、これは profile id ではなく、
  Observation インスタンスの id(`"#{record.id}-#{slug}"`、`serializer.rb:30`)と、その逆引き(`fhir_controller.rb:98`)に使われる

### 2.2 案(R-20261124-7 の問い 5: テンプレートで修飾した id を既定にする)

`Fhir::ProfileIdentity`(新設)が、テンプレート ID とアーキタイプ ID から 4 つを返す。両 generator はこれだけを使う。

| 項目 | 形 | 例(`bmi_calculation`、height) |
|---|---|---|
| `id` | `openehr-<テンプレートの slug>-<アーキタイプの slug>`。slug は `parameterize.dasherize`。64 文字を超えたら、先頭 55 文字 + `-` + 全体の sha256 の先頭 8 桁 | `openehr-bmi-calculation-observation-height-v2` |
| `url` | `urn:openehr:<template_id>:<archetype_id>` | `urn:openehr:bmi_calculation:openEHR-EHR-OBSERVATION.height.v2` |
| `name` | id の `-` を区切りに camelize(FHIR の name の規則 `[A-Z][A-Za-z0-9_]*`) | `OpenehrBmiCalculationObservationHeightV2` |
| `title` | `openEHR <concept の humanize> (<template_id>: <archetype_id>)` | `openEHR Height (bmi_calculation: openEHR-EHR-OBSERVATION.height.v2)` |

- JSON と FSH の `name` はこれで一致する(FSH の `Profile:` は従来から id 由来なので、FSH 側は「修飾が付く」だけ)
- アーキタイプだけの id を出すオプションは作らない(使う人がいない。必要になったら足す)
- `Entry#slug`(インスタンスの id)は変えない。2 つのモデルが同じアーキタイプを使うと、`"1-<slug>"` がモデルをまたいで重なりうる(推論)。
  別の Issue に起票する

### 2.3 Red から始める spec の見出し

- 「同じアーキタイプを使う 2 テンプレート(`problem_list.opt` と `jp_referral.opt`)の profile id が衝突しない」(JSON・FSH の両方)
- 「JSON の id・url・name と、FSH の `Id:`・`Profile:` が同じ表から出る」
- 「id は 64 文字以内で `[A-Za-z0-9\-\.]` だけ。長いテンプレート ID では sha256 の接尾辞で切り詰める」
- 既存の id・url・name・title を固定している例と golden FSH(`spec/fixtures/fsh/…`)は、新しい形に書き換える(golden のファイル名も id に合わせる)
- regression pin: 写像の中身(differential、FSH の規則行)は変わらない

### 2.4 Upgrade note に書くこと

- StructureDefinition の id・url・name・title が変わる。`app/fhir/profiles/<id>.json` のファイル名も変わる(`--fhir` で書き出したものは再生成が要る)
- 外部から profile の url を参照している場合(インスタンスの `meta.profile` など)は付け替えが要る。このリポジトリの serializer は `meta.profile` を書かない(実測)

## 3. `Storable` の書き込み経路(#61・#62・#69)

0.9.0 の歯止め(#60)で止めている 3 つの形を、正しく組めるようにする。歯止めは形ごとに外す(1 Issue = 1 PR)。

### 3.1 共通: entry の単位

- いまは `field[:archetype_id]` で entry をまとめる(`storable.rb` の `rm_content`)。これを、field の path の
  **entry の部分**(先頭から entry ルートの `[archetype_id]` まで)と、entry の何番目の出現か、でまとめる
- 何番目かは、0.9.0 で足した `instance_index` から決める。`instance_index` を持たない `FIELD_MAP`
  (0.9.0 より前に生成したもの)は、SECTION・埋め込みルート・INSTRUCTION を含むなら歯止めを残し、
  メッセージを「0.9.0 以降で再 scaffold してください」に変える

### 3.2 #61 埋め込み CLUSTER

- path の埋め込みルートのセグメント(0.9.0 から `[archetype_id]`)を、`_type: CLUSTER`・`archetype_node_id: <archetype_id>`・
  `archetype_details` を持つノードとして組む。0.9.0 より前の path(`[at0000]` 形)は 3.1 の歯止めで止める
- 同じ path に 2 つのルート(`jp_referral` の organisation ×2)は、`instance_index` で別のノードにする
- Red: 「`lab_result_report_reduced` のモデルが、OBSERVATION 1 つの中に埋め込み CLUSTER を持つ Composition を保存し、`rm_graph.to_rm` で組み直せる」

### 3.3 #62 SECTION

- path の entry より前の部分(`/content[SECTION]/items[ENTRY]`)を、`content` 配下の `SECTION` ノード(`archetype_details` つき)と、その `items` として組む
- 同じアーキタイプの entry の繰り返し(`clinical_synopsis` ×2)は別の entry にする
- Red: 「`jp_referral` の EVALUATION と OBSERVATION の値を入れたモデルが、`content: [SECTION { items: [...] }]` を保存し、`to_rm` で組み直せる」

### 3.4 #69 INSTRUCTION

anlage の規則にそろえる(R-20261124-19)。正は anlage の設計書 `docs/design/rm-attributes-without-inputs.md` 6 節「決めたつなぎ方」
(読んだのは anlage PR #116 の `edbdb18`。実装は同じ PR の `app/lib/opt/composition_builder.rb` の `narrative`・`narrative_value`)。

| 属性 | 値の出どころ |
|---|---|
| `narrative`(DV_TEXT、必須) | 下の「つなぎ方」 |
| ACTIVITY の `description` | field の path から組む(いまの `new_rm_node` と同じ) |
| ACTIVITY の `action_archetype_id`(必須) | OPT の制約(`action_archetype_id` の C_STRING のパターン)。無ければ `/.*/` |
| ACTIVITY の `timing` | 付けない(RM 1.0.4 で任意) |
| 入力がひとつも無い INSTRUCTION | 組まない(値の無い field は entry を作らないので、いまの動きのまま) |

つなぎ方(anlage の 6 節のとおり):

- 対象: INSTRUCTION の配下(activities と protocol、埋め込み CLUSTER の奥も含む)で値が入った要素。空欄は含めない
- 並び: field の並び(OPT の文書順。`FIELD_MAP` の順)
- 1 要素は「ラベル: 値」。埋め込みルートの配下の要素は「ルートのテンプレート上の名前／ラベル: 値」(例: 「住所／市区町村: 文京区」)
- 値: 帳票で見えるとおり。選択肢は表示名(`code_labels`)、数量は「値 単位」、日時は「日付 時刻」(時刻があれば)。そのほかは入力のまま
- 区切り: 全角のセミコロン「；」。**改行は使えない**(DV_TEXT は改行を持てない。RM の不変条件)。
  この節の初版(`f659d7b`)は改行区切りとしていたが、R-20261124-19 で改めた
- 生成系は使わない

ルートのテンプレート上の名前は、field に新しいキー(`root_label`)として載せる。openehr 2.5.0 はルートごとの用語を持つ
(openehr-ruby#58、`CArchetypeRoot#term_definitions`)ので、ルートの at0000 の text をそこから取る(推論: 2.5.0 の API。実装の前に実測する)。

`action_archetype_id` を `Storable` が知るには、`FieldExtractor` が entry に ACTIVITY ごとの制約を載せる必要がある
(追加のキー `activities: [{ path:, action_archetype_id: }]`。公開 API の追加なので、changelog に書く)。

- Red: 「`jp_referral` の INSTRUCTION に値を入れたモデルが、narrative と ACTIVITY の `action_archetype_id` を持つ Composition を保存し、`to_rm` が近似(0.8.0 の既定値)を使わずに組み直す」
  「narrative は入力された要素だけを文書順に『ラベル: 値』で改行区切りにつないだもの」
